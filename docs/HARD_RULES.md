# 硬性规则（用户明确要求，不可协商）

> 本文件是**用户原话要求**的整理，不是推断。每条都标了出处。
> 修改本文件前必须得到用户明确同意。
> 做任何创作、修改、保存之前，先读完这一页。

---

## R1. 模板必须从秀米模板库找，不能自己打

**用户原话**
- 「不要你自己打出来，我要你去看秀米提供的模板，看哪些合适，没有就点刷新继续看，找到之后点击加入」
- 「你的标题、章节和分割线都是自己打出来的，和我要求的必须从模板库里找这个要求对不上」

**要求**
- 标题、章节标题、分割线、装饰元素——**全部**用秀米模板库里的真实组件
- 用 `xiumi_template` 搜 → `xiumi_component` 插入（`templateId` 或 `query`+`index`）
- 不合适就点「换一换」继续看，**不许将就**
- 禁止手打 `━━━` `✦` `❖` `★` `===` 这类符号假扮装饰

**例外**：模板库里确实没有对应类型时，必须**明确告诉用户**「这个类型模板库没有，我用了手写样式」，得到同意才能手打。不允许默默手打。

---

## R2. 模板配色必须与推文主题一致

**用户原话**
- 「使用的秀米模板应该符合推文主题，比如推文总体风格为绿色，则使用绿色风格的秀米素材」

**要求**
- 先定这篇推文的主题色/整体调性，再挑与之协调的组件
- 组件色系、风格要跟正文、背景、内容氛围统一；具体用哪个色系由这篇的主题决定，没有固定绑定
- 换主题就换组件，不许沿用上一篇的组件配色

**检索方法**
```
xiumi_template(action='search', query='绿色')          # 按色系
xiumi_template(action='search', query='简约')          # 按风格（会返回各色系列）
xiumi_template(action='search', query='分割线')        # 按类型
```
每个结果带 `id` / `title` / `tags` / `preview`，看 `title` 里的「系列名」判断配色与风格。

---

## R3. 每段文本一个独立 cell

**用户原话**
- 「我要求你的每一段文本都是独立的新的单元格」

**要求**
- 每个自然段 = 一个独立的正文 cell，不许把多段塞进一个 cell
- 实现：`xiumi_write` 传多段 `paragraphs` 时内部会逐段「后插空行」再输入
- 手工操作对应关系：选中 cell → 浮动工具栏「后插空行」→ 新空 cell → 输入

---

## R4. 插图必须按段落位置落位

**用户原话**
- 「图片的占位为什么都是在最下面，而不是按照原推文那样一段一张图」

**要求**
- 图要插在它应该出现的那段之后，**不许**全堆到文末
- 用 `xiumi_image_insert(afterText='锚点文字')`，锚点取该位置前后唯一的一句话
- 插图会切开 cell、变更索引，所以**多图必须串行**：插一张 → `xiumi_edit(action='inspect')` → 重算下一个锚点 → 再插

---

## R5. 背景必须正确

**用户原话**
- 「背景的图层位置也放错了，太低了，我看那些字体的下面依旧是白色背景」

**要求**
- 整篇底色要铺满，不能只有文字块有底色
- 已知限制：秀米纸张背景是 `div.tn-page-vessel` 上的白色 PNG（data URI），其 Angular scope 拿不到 page 对象，**插件目前改不了纸张背景**
- 可行替代：用带底色的**卡片组件**把正文包起来（具体用哪个按本篇主题挑，不要照抄上一套）
- 不许假装做完——做不到就明说

---

## R6. 不要素

**用户原话**
- 「怎么好看怎么来，反正不要那种很素的」

**要求**
- 标题要有装饰组件，不要只有一行黑字
- 章节之间要有分割或卡片，不要光秃秃的段落堆
- 但也不要堆砌到看不清内容——花哨要有节奏

---

## R7. 不要频繁关闭/重启浏览器

**用户原话**
- 「检查为什么工作这么慢，而且老是关闭又启动浏览器。这样做不对，应该在一次打开浏览器后持续进行操作」
- 「让插件可以像人一样在登陆后点击各种功能，想要返回的时候就点返回或者通过点击其他按钮实现返回」
- 「这个要求是写进插件里的」

**要求**
- 登录一次，浏览器一直开着
- 站内跳转用 `xiumi_browser(action='back'|'home'|'editor'|'list')`，**不许** close + open
- 离开编辑中的稿子前必须自动保存或拦住

**已实现**：`_current_page()` 不再因窗口丢失就 teardown；`xiumi_nav`；未保存守卫

---

## R8. 改旧文要在原图文上改

**用户原话**
- 「你不能直接改旧的图文吗」
- 「你却是新建了很多个图文，然后吧内容复制粘贴过去，这样不对，因为创建了很多个无用的图文」

**澄清**（用户后来补充）：「改旧文而不新建」**不是硬性禁令**，是要**具备这个能力**；判断错了才出问题——用新建顶替「改这篇」才是问题。

**要求**
- 用户说「改这篇」→ `xiumi_articles(action='open', articleId=...)` + `xiumi_edit`
- 用户说「再写一篇」→ `xiumi_articles(action='new')` + `xiumi_write`
- 每新建一篇都会在「我的图文」里留一条记录，**用户会看到垃圾稿**

---

## R9. 每次创作前必须先读指导

**用户原话**
- 「我需要你每次都先阅读指导和学习相关的知识再进行创作，否则创作出来的都是低质量」
- 「这个是硬规定，需要写进插件要求」

**要求**
- 创作/修改前先调 `xiumi_guide(action='guide', intent='...')`
- 已实现**硬门禁**：未读指导直接调 `xiumi_write`/`xiumi_compose`/`xiumi_edit`/`xiumi_component` 会被拒绝
- 指导有效期 60 分钟，超时需重读

---

## R10. 创作完必须保存并确认

**用户原话**
- 「每次创作完毕之后，应当点击保存，确定秀米保存好再进行其他的修改」

**要求**
- 写完必须 `xiumi_articles(action='save', confirm=true)`
- 检查返回的 `saveVerified`，`false` 就是没验通过，不许当成功
- 没有 `saveVerified: true` 之前，不许开始下一轮修改

---

## R11. 创作完必须审核打分 + 给修改方案

**用户原话**
- 「应当有对于创建完之后的秀米图文进行审核与评估打分，给出进一步的修改方案之后进行提问是否修改」

**要求**
- 保存后调 `xiumi_review`，把 `score` / `grade` / `findings` / 建议展示给用户
- 然后问用户「要不要按建议改」，**不许**自己改完才说

---

## R12. 遇到问题要截图读提示

**用户原话**
- 「当遇到无法解决的问题时，应当直接对浏览器页面进行截图然后读取页面的提示，而不是半天都不知道保存」

**要求**
- 卡住时先 `xiumi_browser(action='screenshot')`，把图给自己看也给用户看
- 插件在工具异常时会自动截图并把 `screenshotPath` 塞进错误响应

---

## R13. 账号

- 账号与密码由用户在 **DSH 设置页「秀米助手」** 里填写，保存到本机用户目录下的 `config.json`（路径由插件 `config.js` 决定，不写死在文档里）
- 设置页里输入什么账号，就登录什么账号
- **密码不进日志、不进 stdout、不进源码、不写进任何提交物**
- 换账号只需在设置页改，不要在代码里硬编码

---

## R14. 隐私脱敏

**用户原话**
- 「秀米模板库目录这种数据可以持久化的放在插件里，随着工程文件上传到github，但是账号密码啥的不行」

**要求**
- 发布前跑 `node scripts/privacy-check.mjs`，必须 `PASS (0 findings, 0 warnings)`
- 不许有盘符路径、用户名、主机名、账号密码、cookie、token

---

## R15. 少重复请求（成本）

**用户原话**
- 「主要是api请求要钱，而且很贵，所以尽量少重复这么多访问请求的动作」
- 「必要的访问、汇报和验证不能省」

**要求**
- 一个任务只 open 一次浏览器，跨任务复用会话
- 合并测试，别写一次性探索脚本
- 但必要的验证和汇报不许省

---

## R16. 不要冗余功能

**用户原话**
- 「你往好的方向优化，不要有冗余功能」

**要求**
- 功能重叠就合并或删掉
- 新增能力前先确认现有工具覆盖不了

---

## R17. GitHub 红线

**要求**
- 不经用户**明确同意**，不建仓库、不加 remote、不 push、不改 GitHub 设置
- 只读查看（`gh auth status`、`git ls-remote`）可以
- 这条是用户反复强调过的，违反过一次

# 图文制作指南

本指南用于Agent从阅读目标组织图文，再通过安全接口修改和验收。**硬规定**：每次创作或修改前必须先调用 `xiumi_guide(action="guide", intent="本次阅读目标、题材、平台及限制")`；未读时产出型工具直接拒绝，读过之后 60 分钟内有效。工具返回的可用方法需结合原稿选择。六篇公开样例提供的是方法证据，不是统一模板或素材库。

> **用户硬性要求见 [`HARD_RULES.md`](./HARD_RULES.md)**（R1–R17）。本指南讲「怎么写得好」，那份文件讲「哪些做法被明确禁止」——冲突时以 HARD_RULES 为准。最要紧的四条：**R1 标题/章节/分割线必须用秀米模板库组件，不许手打**；**R2 组件配色必须与主题色一致**；**R3 每段独立 cell**；**R4 插图按段落位置落位**。

## 1. 先确定读者要完成什么

阅读原稿、图片和用户要求，先列出保留的信息、可改范围、读者的阅读任务及图片与章节的对应关系，再选结构：

- **并列主题卡片**：多个主题、人物或分享同等重要时，重复“短标题—主图—说明”或“短标题—文字—图组”。保持宽度和标题语法一致，内容长度可以不同。错误例：因样例有三节，就把原稿硬拆成三节。
- **过程叙事**：读者需要理解发生了什么、为什么和结果时，按事实顺序使用导语、短段与代表照片。错误例：把每张照片都升格成一章，打断事件经过。
- **作品图集**：读者主要看画面时，短导入后按题材或场景分组，少量必要图注即可。若同时需要讲经过，先完成过程说明，再进入图集。错误例：每张作品附重复长文，或把所有图片塞进一张无限延长的卡片。
- **阶段推进**：赛事、演出、项目存在真实阶段时，用连续编号和节点大图串联，细节图组补充瞬间。错误例：为了画面变化调换事实先后。

一篇可以组合两种结构，但每次转换要有清楚的部分标题或短导入。章节数、篇幅、图片数随内容决定；不自动添加关注引导、口号或无依据的结论。

## 2. 建立少而稳定的阅读层级

先定正文基准，再定主标题、章节标题、辅助信息。章节标题可通过适度放大、加粗和位置区分，不强制为正文的固定倍数。标题写主题或动作，正文一段集中讲一件事；长段按语义拆分，不能为满足字数打断因果。居中用于少量短开场、标题或署名，连续说明恢复稳定的左侧阅读起点。

六篇桌面预览中，正文约14–16px、行高约1.6–1.9；章节标题约17–20px。卡片内边距约14–20px，图间隙约10–20px。这些是可选起点，封面SVG计算字号还可能被缩放，不能直接作为手机标准。段距、模块间距、卡片内边距分别控制；章节之间比普通段落留白更大。使用明确样式表达留白，不靠连续空段、空格和回车堆出高度。

配色先分角色：浅底板或白底、主题主色、少量强调色，正文优先深色。标题、边线、局部图形共享主色；不要让每个关键词都变色。浅彩字、大字间距、强阴影应在目标设备验证后使用。错误例：为贴合蓝色主题，把整篇正文变成浅蓝并叠加浅底。

## 3. 让图片提供信息

先核对每张图片的用途、自然横纵比、主体位置、清晰度和顺序。合照、关键节点和含细节资料的图优先接近正文宽度单列展示，保持比例；截图、图表中的小字必须能读。裁成方形或圆形前检查人物、手势、展示板和边角信息，不能拉伸填满容器。

同一内容单元的照片可组成双图或网格。横竖混合时，可用不同栏宽、保留比例并底边对齐，或直接上下排列；不要强裁成统一方格。多张可安全裁切的细节图才适合等大网格。图组保持一致间隙与清楚边界；分栏导致主体太小时改为单列。错位叠图只用于允许局部覆盖的现场瞬间，不用于名单、资料截图或需要精读的图。

章节标题先交代主题，主图紧邻相关段落；图注放在对应图片下方，或图组边缘的专用留白处，避免跨章漂移和遮挡主体。统一图组轴线，不要求所有照片同高。错误例：照片已进入下一节，说明仍留在上一卡片；装饰标签占住人脸。

## 4. 用容器和装饰说明关系

分割线表示话题转换或正文与署名的边界，不在每段之间重复插入。短导语可用上下细线和留白轻量框定。边框与底色卡片用于聚合一节相关文字和图片；内边距保证呼吸感，层层套框不会增加信息层级。直角、轻圆角或无框按题材选择，一篇保持一致的组件语法。错误例：每个短段套不同颜色、不同圆角的卡片。

使用可编辑文字、CSS结构、SVG图形和图片素材分别承担文字、布局与装饰。不得手打星号、长线等装饰字符来假扮组件。标题外观像海报也可能保留真实文字；检查组件模型、文字格和填充结果，不能仅凭截图或 `filled:[]` 判断文字已画在图片里。SVG的 `foreignObject` 有文字也不代表当前编辑器逐项可改。先验证可填字段，再使用组件；需要装饰媒体时选有权使用的素材，不搬运样例品牌、二维码和原图片。

横向图库、叠图、动效和复杂SVG先验证目标平台支持。横向溢出或操作提示只说明有这种结构，不证明手机手势与微信端可用。重要信息应在默认可见路径中；无法实测或不兼容时，降级为纵向图组、完整单图和简单可编辑标题。

## 5. 按明确范围编辑与保存

1. **取得指引**：先调用 `xiumi_guide action=guide`。用户给外部样例时，调用 `xiumi_guide(action="learn", url="外部样例链接")`，只积累可泛化方法；读取失败要报告，不能凭空补成已学习。
2. **绑定目标**：修改现稿先 `xiumi_articles action=open`，再 `xiumi_edit action=inspect`，取得并核对 `articleId`、`revision` 和明确cell列表。区分正文、图片、组件及应保留部分。用户要求改现稿时不得新建替代。
3. **形成局部计划**：将内容和样式改动映射到本次inspect返回的格。多格 `replace_body` 必须提供明确的 `cellIndexes`；未选组件不动。单格使用对应 `cellIndex`。可带 `expectedRevision` 防止旧计划覆盖新状态；文章结构改变后重新inspect，不能沿用旧编号。
4. **执行并预览**：`xiumi_edit` 所有写动作都必须 `confirm=true`，其含义是执行已获授权的具体范围。`save=false` 只产生未保存预览。需要离开脏稿时，显式保存确认或按用户明确要求传 `discard=true`；导航、切稿和关闭不会偷偷代为保存。
5. **保存对账**：需要保存时使用 `xiumi_articles(action="save", confirm=true)` 或已授权写动作的显式保存选项。分别检查 `saved` 与 `saveVerified`：前者是保存操作结果，后者必须来自独立页面读取并比较正文模型、样式、组件及图片顺序。两者成功且无未解释差异，才报告保存完成；toast、文章ID、标题或字数相同均不能单独证明保存完整。
6. **处理未知状态**：超时、取消、断连可能发生在写入之后。先inspect对账，确认实际结果与当前版本，再决定补做；不要直接重试，避免重复插图、重复组件或误覆盖。保存未验证时清楚报告未确认项。
7. **验收交付**：运行 `xiumi_review`，结合截图检查标题层级、段落、图片顺序/裁切、留白、未选组件保留和占位内容清理。评分只是线索；截图和模型共同证明结果。交互、手机版及微信端分别实测，未测就明确标注，不能宣称已兼容。

## 6. 让经验可追溯

完成实测后，用 `xiumi_guide action=feedback` 按 `ruleIds` 记录 `outcome=success/failure`，写清适用任务与已验证效果。失败也应反馈，不能只积累“成功”。自己的作品只作为实践反馈，不能再当外部样例增加证据；重复来源不重复计数。

依据见 [批次A](research/layout-a.md)、[批次B](research/layout-b.md) 及对应学习数据。区分 `observed`、`inferred` 与制作建议；置信度不等于用户偏好。B3含模板残留，圆图、横滑等只作条件性技法，不据此自动继承整套风格。六篇样例均未证明移动端、微信清洗后或原编辑器的逐项可编辑性。
